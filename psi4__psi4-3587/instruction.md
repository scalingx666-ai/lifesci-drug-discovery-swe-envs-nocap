# Issue

**Title:** Separate orbital canonicalization from occupation assignment

## Description

## Description

`HF::form_C` does two independent things: it forms the MO coefficients from the current
Fock matrices, and it then assigns the occupation by the aufbau rule. Only the pair is
callable, so a caller that has already optimized against a particular occupation cannot ask
for canonical orbitals without having the occupation reassigned underneath it.

That is a real need for a second-order optimizer, which works at fixed occupation and
should hand back the solution it converged. Calling `form_C` to canonicalize can move the
occupation off that solution, leaving the wavefunction describing two different
occupations at once: the density rebuilt at the new one while the Fock matrix and energy
still describe the old.

Split the first half into a virtual `canonicalize_orbitals`, leaving `form_C` as the
composition, defined once in the base:

```cpp
void HF::form_C(double shift) {
    canonicalize_orbitals(shift);
    find_occupation();
}
```

The four references override the new method instead. Their bodies are unchanged apart from
dropping the trailing `find_occupation()`, which in each case was a single call near the
end. `form_C` keeps its behavior and stays virtual, so every existing call site is
unaffected and any out-of-tree override still compiles and works.

Split out of the OpenTrustRegion interface PR, where it is what lets the solver return the
occupation it optimized. It stands alone and changes no behavior, so it seemed worth
reviewing on its own.

## Questions
- [ ] **Naming.** `canonicalize_orbitals` is accurate for RHF and UHF, where the method
      diagonalizes the Fock matrix. ROHF and CUHF diagonalize an effective Fock, so "canonical"
      there means canonical with respect to that operator. I avoided `semicanonicalize` because
      `Wavefunction::semicanonicalize()` already exists and is called from `proc.py` for
      ROHF-based correlated methods, and because it names the occ-occ/virt-virt block
      diagonalization rather than this. Happy to take a better name.
- [ ] Should the new method be virtual on `HF` as done here, or would you rather `form_C` stop
      being virtual now that the base implementation is meaningful? Keeping both virtual is the
      conservative choice for out-of-tree code, at the cost of two overridable entry points.
